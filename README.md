# LinkedIn API — SaaS Dashboard, Auth, Connection & Accounts

> **Current focus:** a public dashboard (sign-up, API keys, extension download,
> docs), the connector extension, and connected-account management —
> **running end to end on Windows, verified live in a real browser, no Docker.**
> Search and reactions (below the fold) are built and typechecked but parked —
> not the active path. Full design: [MVP.md](MVP.md) · destination platform:
> [PLAN.md](PLAN.md)

## The SaaS surface (`api/public/`)

Static pages served by the same Hono app, same-origin, cookie-authenticated
(no bearer-token juggling needed — unlike the extension, which is cross-origin
from `chrome-extension://` and must use a bearer token).

| Page | What it does |
|---|---|
| `/` | Landing page |
| `/signup.html`, `/login.html` | BetterAuth email/password, redirects to `/dashboard.html` |
| `/dashboard.html` | Download the extension · connected LinkedIn accounts · create/list/revoke API keys |
| `/docs.html` | Full API reference, generated by hand from the actual route files (not auto-generated OpenAPI — see Status) |
| `/downloads/linkedin-connector.zip` | The extension, zipped. Regenerated by `npm run build:extension` (wired into `dev`/`start`) |

API keys are minted via `POST /v1/me/keys`, which wraps BetterAuth's own
`auth.api.createApiKey` — verified by reading the compiled plugin that
`references: "organization"` makes every create/list/delete check real org
membership server-side (`checkOrgApiKeyPermission`), not something this app
re-implements.

## Why two languages, one database

| Tier | Stack | Owns |
|---|---|---|
| **`api/`** | Node · Hono · **BetterAuth** · Drizzle · **SQLite** | Auth, organizations, API keys, tenancy, the public REST API |
| **`worker/`** | Python · FastAPI · **curl_cffi** · **SQLite** | Everything that touches LinkedIn: session vault, transport, Governor, adapters, circuit breaker |

The language split is forced by one verified fact: the only way to present a
real Chrome TLS fingerprint is `curl_cffi`, which is Python-only. Node's default
JA3 is rejected by LinkedIn before any JavaScript runs. BetterAuth is
TypeScript. So the tiers are chosen per job.

**Both processes share one physical SQLite file** (`dev.db` at the repo root) —
no Postgres, no Redis server, no Docker for this milestone. Node/Drizzle owns
the schema and migrations; the Python side speaks raw `sqlite3` against tables
Drizzle created, encoding timestamps/booleans/JSON exactly the way Drizzle does
so both sides read each other's rows correctly. SQLite's own file locking makes
this safe for one writer process per language; see the comment at the top of
`worker/app/db.py` for what would need to change to run multiple worker
processes against the same file.

**The Python service is never publicly routable.** It has no tenant model; it
trusts `x-internal-token` and is only ever called by the API tier.

## Setup

```bash
cp .env.example .env    # then fill in the generated secrets
```

Generate the secrets:

```bash
python -c "import os,base64,secrets;print('VAULT_KEY='+base64.urlsafe_b64encode(os.urandom(32)).decode());print('BETTER_AUTH_SECRET='+secrets.token_urlsafe(32));print('INTERNAL_TOKEN='+secrets.token_urlsafe(32))"
```

`DATABASE_PATH` in `api/.env` and `worker/.env` must both resolve to the **same
file**. Since each process is launched with its own directory as `cwd`, set it
relative to that directory — `../dev.db` in both, so `api/../dev.db` and
`worker/../dev.db` land on the same repo-root file. (The root `.env.example` and
`.env` use `./dev.db` since nothing runs from the root itself.)

### API tier

```bash
cd api && npm install
npx drizzle-kit push --force   # creates dev.db + all tables
npm run dev                    # http://localhost:3001
```

### Worker tier

```bash
cd worker && python -m venv .venv
.venv/Scripts/python -m pip install -e ".[dev]"
.venv/Scripts/python -m uvicorn app.main:app --port 8001
```

Ports are **3001** (API) and **8001** (worker) in this checkout, not 3000/8000
— picked to dodge other local processes already on those ports. Start the
worker on **8001**: `api/.env`'s `LINKEDIN_SVC_URL` points there, and a worker
running on any other port makes every `/v1/search/*` and `/v1/linkedin` call
return `503 provider_unavailable / "fetch failed"` while the worker's own
`/internal/health` looks perfectly fine. That pair of symptoms means a port
mismatch, not a broken worker. Change
`PORT`/`BETTER_AUTH_URL` in `api/.env`, `INTERNAL_PORT` in `worker/.env`, and
`LINKEDIN_SVC_URL` in `api/.env` together if you move them, and update
`extension/config.js` + `extension/manifest.json`'s `host_permissions` to match.

⚠️ **Env vars load once at process start.** Changing `.env` requires a full
process restart (kill + relaunch) — `tsx watch`'s file-reload does not
re-read `.env`. This bit the initial verification pass (see Status below).

## Two auth models, side by side

| | Session auth (`/v1/me/*`) | API-key auth (`/v1/*`) |
|---|---|---|
| **Who** | A signed-in human, or the extension acting for them | An external machine consumer |
| **Credential** | Bearer token from BetterAuth (`/api/auth/sign-in/email`) | `x-api-key` header |
| **Tenant comes from** | `session.activeOrganizationId` | the key's `referenceId` (the plugin runs with `references: "organization"` — the key itself *is* the tenant claim) |
| **Mounted** | Outside the `/v1` API-key gate, in its own sub-app | Behind `v1.use("*", apiKeyAuth())` |

Both write to the same `linkedin_accounts` table; they are two doors into the
same room. `/v1/me` is what the extension actually calls. `/v1/accounts` is for
a future external consumer minting its own key and is a straight port of the
same logic (see MVP.md §9 for that full contract) — not part of the current
focus.

A first-time sign-in has no organization yet: `GET /v1/me` creates one and
marks it active automatically, so the extension never has to know
organizations exist.

## API — current focus

### Auth (BetterAuth, mounted at `/api/auth/*`)
```
POST /api/auth/sign-up/email
POST /api/auth/sign-in/email
POST /api/auth/sign-out
```
Each response carries the session token in a `set-auth-token` header (from the
`bearer` plugin) — that is what the extension stores and sends back as
`Authorization: Bearer <token>`.

### Session-authed: `/v1/me/*` — what the extension calls
```
GET    /v1/me                        # who am I, my org (auto-provisioned if new)
POST   /v1/me/accounts/connect       # from the extension, after reading li_at/JSESSIONID
GET    /v1/me/accounts               # the connected-accounts list
GET    /v1/me/accounts/:id
PATCH  /v1/me/accounts/:id           # pause / resume
DELETE /v1/me/accounts/:id
```

### API-key-authed: `/v1/accounts/*` — for an external consumer, not the extension
```
POST   /v1/accounts/connect
GET    /v1/accounts
GET    /v1/accounts/:id
GET    /v1/accounts/:id/limits       # live quota
PATCH  /v1/accounts/:id
PUT    /v1/accounts/:id/limits
DELETE /v1/accounts/:id
```

### `/api/v1/*` — Unipile-compatible facade

A consumer written against Unipile changes **only its base URL**. The facade
(`api/src/compat/`) mirrors Unipile's paths, request shapes, response envelopes
and the status codes consumers branch on — `{ items, cursor, paging }` for lists,
`{ data }` for the Magic Route, `{ type: "errors/…", status }` for errors, the
same `X-API-KEY` header, the same OK/CREDENTIALS/CHECKPOINT account vocabulary.

It does one thing Unipile refuses to: every response also carries
`provider_status`, `provider_body` and `outcome`. Unipile strips LinkedIn's
error body, so a wrong route, a wrong finder, a bad value and a nonexistent
route all return one identical opaque 400 — that opacity is documented as its
single most expensive property by the consumers we studied. Unipile parsers
ignore our extra keys; anyone debugging gets the real answer.

Served today: `POST /linkedin`, `POST /linkedin/search` (url variant),
`GET /linkedin/company/{id|vanity}`, `GET|POST|DELETE /accounts[/{id}]` (cookie
connect; password login → 501), `GET /users/me`, `GET /users/{identifier}`.
Everything else Unipile offers returns `501 errors/not_implemented` **with the
closest working alternative in `detail`** — most are reachable now through the
Magic Route.

The contract it was built against — 86 endpoints, every field alias and status
semantic two production consumers were observed to depend on — lives in
[`docs/unipile-reference/`](docs/unipile-reference/).

### `POST /v1/linkedin` — raw governed passthrough

One endpoint that forwards an arbitrary LinkedIn request through a connected
account's live session. This is what makes the rest of LinkedIn reachable
without a bespoke endpoint per surface — profile and company reads, page
settings, org and creator analytics, invitations, comments, follows,
notification cards. Studying how a mature product actually consumes the
commercial equivalent of this API, roughly a third of every call it makes is
this single route with a different URL.

```
POST /v1/linkedin
{ "account_id", "request_url", "method"?, "op_class"?, "body"?, "headers"? }
→ 200 { "data": { "outcome", "provider_status", "provider_body",
                  "provider_json", "rejection_kind", "reason" },
        "meta": { "quota", "notes" } }
```

Three properties are the point:

**LinkedIn's status and body are never stripped.** A LinkedIn 400 or 403 comes
back as HTTP 200 here with `provider_status` and `provider_body` intact, because
a refusal is the answer you asked for, not a failure of the call. The incumbent
swallows both, and it is their most expensive flaw: a wrong route, a wrong
Rest.li finder, a wrong action name and a wrong payload all return one identical
detail-free 400 — the same thing a nonexistent route returns — so payload work
becomes unfalsifiable guessing. Verified live here: a nonexistent Voyager
resource returns **404**, cleanly distinguishable from a 400, with LinkedIn's
own error body attached. Our own status codes stay reserved for our own
conditions, so LinkedIn's 429 and our quota 429 can never be confused.

**It is governed.** The call goes through the same single egress choke point as
everything else, so the quota Governor, circuit breaker, pinned user-agent,
Chrome TLS fingerprint and per-account proxy all apply. `op_class` (`READ` or
`WRITE`) decides which budget it spends; any mutating method must declare
`WRITE`, and writes get a far tighter budget than reads because write volume is
what actually gets accounts restricted.

**The outcome is a three-way discriminant, never a null.** `ok`, `rejected`
(definitively refused — did not take effect, safe to retry or try another
approach) or `ambiguous` (timeout, 5xx, or a 2xx mutation with an unreadable
body — it *may* have landed). For a mutation that distinction is the whole
ballgame: blind-retrying an `ambiguous` non-idempotent write is how you create a
duplicate company page or email a real person a second invitation. Two things a
caller must know beyond `outcome`: `rejection_kind: "rate_limited"` is the one
`rejected` you should not immediately retry, and **a 2xx does not prove a field
was written** — LinkedIn accepts and silently ignores Rest.li `$set` keys it
doesn't recognise, answering 200 while changing nothing, so verify partial
updates by reading the entity back.

Security boundary: `request_url` is host-allowlisted to `www.linkedin.com`
(credentials-in-URL and non-443 ports refused), redirects are never followed,
and session-bearing headers are dropped — notably `csrf-token`, because one
copied from a captured browser request is matched against the JSESSIONID we
attach and is guaranteed to mismatch. Send `accept` and `x-restli-*`; we supply
the token.

## The extension (`extension/`)

MV3, vanilla JS, no build step, no content script.

| File | Role |
|---|---|
| `popup.html` / `popup.js` | Sign in / sign up, "Connect this account" button, connected-accounts list with remove |
| `background.js` | `chrome.alarms`-driven silent session re-push every 60 min, so the vault stays warm without the popup ever being open |
| `linkedin-session.js` | The **only** touch point with linkedin.com: a local `chrome.cookies.get` for `li_at` + `JSESSIONID`. No DOM access, no request to linkedin.com — this is what keeps it invisible to LinkedIn's own detection |
| `api.js` | Talks to the backend; captures `set-auth-token` on every response |
| `storage.js` | `chrome.storage.local` — the bearer token and a small cached "me" object only. **Never** LinkedIn cookies |

Load it: `chrome://extensions` → Developer mode → **Load unpacked** → select
`extension/`.

Two real cross-origin gaps a plain implementation misses, both handled in
`api/src/index.ts` and `auth.ts`:
- **CORS.** A `chrome-extension://` origin sending a custom `authorization`
  header forces a preflight. `hono/cors` is configured with a predicate (an
  extension's origin is unique per install, not a fixed string) and
  `exposeHeaders: ["set-auth-token"]` — without that second one, the browser
  hides the header from JS and sign-in silently never captures a token.
- **`trustedOrigins`.** BetterAuth's own origin check is separate from CORS;
  `"chrome-extension://*"` is verified (by reading `trusted-origins.mjs`) to
  hit the genuine wildcard-match path for custom schemes, not a literal string
  compare.

## Three properties worth knowing (parked search/reactions design — Postgres/Redis-era)

These describe the **destination** design in MVP.md/PLAN.md, written when the
plan assumed Postgres + Redis. They still apply conceptually once that path is
un-parked; swap "Postgres" → "SQLite" and note the Redis-based atomic governor
would need a SQLite-safe equivalent (a single `threading.Lock`, like
`worker/app/db.py` already uses, works for one process — the Lua-script version
in `worker/app/governor.py` is written for real concurrent workers against
Redis and is part of what stays parked).

**Reads never reach LinkedIn.** `GET /v1/posts` is served from the store. A
consumer polling hard hits the database, so their request volume cannot push an
account toward a restriction.

**Writes are queued, never synchronous.** `POST /v1/reactions` returns `202` and
an action id. The Governor may defer it by minutes; the worker executes when
allowed. Callers never implement pacing — that is the product.

**Quota checks are atomic.** Concurrent workers share one atomic check-and-increment.
A read-then-increment would let two workers both pass on the last unit, and
overspending the budget is exactly what gets an account restricted.

## Security audit

Ran a multi-agent audit (5 independent reviewers over auth, secrets, injection/XSS,
network, and the extension) with every finding then adversarially re-checked by a
separate reviewer instructed to default to refuting it. 10 raw findings, 3 survived
verification as genuinely exploitable. All 3 are now fixed and verified live; a 4th,
non-exploitable-today hygiene issue was fixed proactively.

| # | Finding | Severity | Fix |
|---|---|---|---|
| 1 | `api/src/routes/actions.ts` called `requireOrg()` but never `requireScope()`, unlike every other `/v1` route — any valid API key for an org could read and cancel every action regardless of its declared permissions (e.g. an `audit:read`-only key could cancel queued reactions). | High | Per-row scope check based on the action's own `service` column; list endpoint silently narrows to readable services rather than erroring. **While fixing this, found and fixed a second, deeper bug: scoped-key creation itself was silently broken** — `POST /v1/me/keys` passed `headers` to `auth.api.createApiKey`, and BetterAuth unconditionally rejects `permissions` on any call that carries `headers`, even though its own `checkOrgApiKeyPermission` had already verified the caller. Every earlier test had happened to omit `permissions`, so this was invisible until the audit's own restricted-key test tripped it. Fixed by passing `userId` directly instead of `headers` — safe because both `orgId` and `userId` come from an already-verified session, not client input. |
| 2 | `dashboard.js`'s `loadAccounts()` rendered the account `label` field into `innerHTML` unescaped — unlike the adjacent key list, which does escape. `label` is settable via an API-key-authed route, so a limited `accounts:write` key could plant a payload that runs in an org teammate's browser under their session the next time they open the dashboard (e.g. silently minting a new unrestricted key and exfiltrating it). | High | Route it through the same `escapeHtml()` already used for key names. |
| 3 | `webhooks.secretEnc` stored the signing secret as **plaintext**, despite the column name and an accompanying code comment both implying it was encrypted. Anyone with read access to `dev.db` could recover every org's secret and forge webhook deliveries. | Medium | Real AES-256-GCM encryption (`api/src/lib/crypto.ts`), reusing the same `VAULT_KEY` the Python worker already uses (as a Fernet key) for LinkedIn cookies — one root secret, not two to manage. |
| 4 | The CORS origin predicate (`origin?.startsWith(...) ? origin : origin ?? ""`) was a no-op — both branches returned the caller's own `Origin` header, so it reflected *any* origin rather than only `chrome-extension://`. Verified as not currently exploitable (BetterAuth's session cookie defaults to `SameSite=Lax`, and `/v1/*` needs a header no browser attaches ambiently), so this was fragile defense-in-depth, not a live hole — fixed anyway since relying solely on a cookie default elsewhere is not a reason to leave a CORS check broken. | — (hygiene) | False branch now returns `undefined`, which Hono's `cors()` correctly treats as "don't allow." |

**Investigated and correctly ruled out** (verifier traced the actual `better-auth`
source rather than taking the claim at face value): the same CORS bug combined with
`trustedOrigins: ["chrome-extension://*"]` — a wildcard that genuinely matches any
installed extension's origin, confirmed by reading BetterAuth's `wildcardMatch`
implementation — but the claimed cookie-theft chain doesn't hold because the
extension never relies on ambient cookies (bearer-token-only, `chrome.storage.local`
is per-extension-id and not shared) and the dashboard is same-origin, so nothing
ambient is actually exposed to reflect. Also checked and found genuinely low-risk:
the internal-token comparison in the Python worker uses `!=` rather than a
constant-time comparison (real, but the service isn't network-reachable in the
current deployment); the extension's `host_permissions` are broader than the one
cookie read it performs (real, but low actual risk); `/internal/health` skips the
internal-token check (intentional — matches the same unauthenticated-liveness-probe
pattern used by `GET /health` on the Node side).

### Real bugs this live run actually caught (not visible from typechecking)

1. **BetterAuth's Drizzle adapter silently needs `schema` passed explicitly** — omitting it fails at request time, not at startup.
2. **The generated auth schema was missing a required column (`issuer` on `account`)** — the external `@better-auth/cli` generator is deprecated and several versions behind the installed `better-auth` core. Fixed by calling `better-auth/db`'s own `getSchema()` to get the ground truth and patching the one real gap, rather than trusting the stale tool.
3. **CORS was fully missing** — a `chrome-extension://` origin sending a custom header forces a preflight; without it every extension call would silently fail in a real browser.
4. **`exposeHeaders` on CORS** — without it, `set-auth-token` is invisible to extension JS even though the request succeeds; sign-in would appear to work while capturing no token.
5. **A shared SQLite connection under a threaded server** (`sqlite3 objects created in a thread can only be used in that same thread`) — FastAPI runs sync endpoints on a thread pool; fixed with `check_same_thread=False` **plus** an explicit `threading.Lock` around every use (the flag alone silences the check without adding real safety).
6. **`extension/api.js`'s `signOut()` sent no body** — BetterAuth rejects a bodyless POST as invalid JSON even though it ignores the content; every body-less call now sends `{}`.
7. **Two stale `.env` values from a port collision** — an unrelated process already held port 3000; moved to 3001/8001, and caught mid-fix that a `cp` had clobbered a per-process relative path with the wrong one.
8. **A route-registration-order bug in `posts.ts`** — the greedy `/:urn{.+}` catch-all was registered before the static `/-/stats` route, so Hono's router matched the catch-all first and `/-/stats` was silently unreachable (returned a `post_not_found` 404 instead of stats). Caught only by actually calling it with a real API key; fixed by moving the specific route before the catch-all, with a comment explaining why the order matters.
9. **`archiver@8` is a full API rewrite** — its documented `archiver('zip', opts)` factory function from every existing tutorial doesn't exist in v8 (`require('archiver')` returns `{ Archiver, ZipArchive, ... }`, not a callable). Pinned to `archiver@7`, which has the classic, stable API — verified both the CJS shape and the ESM `default` import work before writing the packaging script around it.
10. **The dashboard showed a doubled API key prefix (`lk_lk_AUE…`)** — BetterAuth's `start` field already includes the configured `prefix`; concatenating `prefix + start` double-counted it. Caught only by reading the actual rendered page text in a browser, not by inspecting the JSON response shape alone (the bug was in how the client combined two technically-correct fields).

None of these would have surfaced from `tsc --noEmit` or `pytest` alone — they only appear when the real processes actually talk to each other, to LinkedIn, and to a real rendered browser.

### The one thing that is *not*, and cannot be, verified by me

The "success" branch of connect (`ok: true` — a real LinkedIn session accepted)
needs an actual logged-into-LinkedIn Chrome cookie. I don't have LinkedIn
credentials and shouldn't fabricate a login. What **is** proven is the entire
pipeline around that branch: the request reaches LinkedIn with a genuine Chrome
TLS fingerprint, LinkedIn's real response is correctly classified, and the
error path is clean end to end. The only way to exercise the success branch is
for you to load the extension in a real Chrome with an active LinkedIn session
and click Connect — the code path is identical, just with a real cookie instead
of a test one.
